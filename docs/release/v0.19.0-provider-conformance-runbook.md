# v0.19.0 Provider Conformance Rollout Runbook

This runbook is the release gate for the v0.19.0 single-leader, Redis lock, and
Redis rate-limit contract changes. Service owners may tighten these gates, but
must not relax them.

## English

### Before The Canary

- Inventory every caller-owned campaign deadline and every `Group`, `MemberID`,
  `KeyPrefix`, and custom Redis lock token. Remove identities rejected by the
  new structural validation before deploying a new binary.
- Mixed old/new binaries retain generated leader/lock tokens, Redis keys, TTLs,
  and storage formats. The exception is a custom lock token with leading or
  trailing whitespace: v0.19.0 preserves those bytes while older binaries may
  have trimmed them. Do not mix versions for that owner until its token identity
  is migrated.
- Expect an old single Redis leader contender to return `ErrNotLeader`
  immediately, while v0.19.0 waits until acquisition or its caller deadline.
- For `leader/sql`, apply `sqlleader.SchemaSQL` with a migration owner before
  the canary. Verify the exact seven-column catalog, primary key, no hostile
  triggers/RLS, and a runtime role limited to schema usage plus table DML.
  Every endpoint and reconciliation probe must reach the same writable
  PostgreSQL primary; record server identity and HA timeline, and fence the old
  writer before promotion.

### Telemetry And Promotion

Observe campaign wait duration, acquisition, timeout/cancellation, validation
failure, provider failure, `ErrCampaignInProgress`, `ErrCleanupPending`, cleanup
duration, resign retry, TTL fallback, and takeover latency. Separate confirmed,
bare-context, and commit-unknown outcomes. Labels may contain only bounded
backend, operation, outcome, and sentinel categories; never put identity,
endpoint, token, or rendered errors in labels or logs.

Run the canary for at least `max(15 minutes, 10 * maximum leader TTL)` and cover
contention, renewal, resign, and takeover. Promote only when:

- new validation failures and unresolved cleanup-pending records are both zero;
- provider/resign failure and campaign-timeout rates remain within both 20%
  relative and 1 percentage point absolute of the previous stable window;
- campaign-wait and takeover-latency p95 remain at or below 1.2 times baseline;
- every cleanup completes by bounded retry or TTL fallback within two TTLs.
- PostgreSQL pool wait/statement p99 remains inside the
  `Lease-RenewInterval` margin, starvation clears local leadership before
  server-time expiry, and a controlled HA fencing/takeover exercise succeeds.

Hold promotion for any gate breach, raw identifier/error exposure,
goroutine/container leak, cleanup pending beyond two TTLs, or a lease blocking a
new owner. Roll back after a safety/redaction breach or failure to recover across
two consecutive five-minute windows.

### Rollback Completion

Before binary rollback, cancel outstanding campaigns with the service shutdown
context and attempt bounded owner-aware resign. Rollback is complete only after
campaign goroutines are zero, renew traffic is zero, every cleanup is complete
or its remaining TTL is recorded, and a takeover probe succeeds after resign or
TTL expiry. Existing-provider storage formats are unchanged, so they require no
data migration rollback. For `leader/sql`, retain
`public.bluetape_leader_leases` and its grants during binary rollback; table
drop or rewrite requires a later, separately reviewed migration after no
deployed binary uses it.

## 한국어

### Canary 전 점검

- 모든 caller-owned campaign deadline과 `Group`, `MemberID`, `KeyPrefix`, custom
  Redis lock token을 inventory합니다. 새 structural validation이 거부하는 identity는
  새 binary를 배포하기 전에 제거합니다.
- Old/new binary는 generated leader/lock token, Redis key, TTL, storage format을
  그대로 공유합니다. 단, 앞뒤 공백이 있는 custom lock token은 예외입니다. v0.19.0은
  그 byte를 보존하지만 이전 binary는 trim했을 수 있으므로 token identity migration이
  끝날 때까지 해당 owner에서 mixed-version 배포를 하지 않습니다.
- 이전 Redis single leader contender는 즉시 `ErrNotLeader`를 반환하지만 v0.19.0은
  acquire 또는 caller deadline까지 기다립니다.
- `leader/sql`은 canary 전에 migration owner로 `sqlleader.SchemaSQL`을 적용합니다.
  정확한 7개 column catalog, primary key, hostile trigger/RLS 부재, schema usage와 table
  DML만 가진 runtime role을 검증합니다. 모든 endpoint와 reconciliation probe가 같은
  writable PostgreSQL primary에 도달해야 하며 server identity와 HA timeline을 기록하고
  promote 전에 old writer를 fence합니다.

### Telemetry와 Promotion

Campaign wait duration, acquisition, timeout/cancellation, validation failure,
provider failure, `ErrCampaignInProgress`, `ErrCleanupPending`, cleanup duration,
resign retry, TTL fallback, takeover latency를 관측합니다. Confirmed, bare-context,
commit-unknown outcome은 분리합니다. Label은 bounded backend, operation, outcome,
sentinel category만 사용하며 identity, endpoint, token, rendered error는 label이나
log에 넣지 않습니다.

Canary는 최소 `max(15분, 10 * 최대 leader TTL)` 동안 실행하고 contention, renewal,
resign, takeover를 포함합니다. 다음 조건을 모두 만족할 때만 promote합니다.

- 새 validation failure와 unresolved cleanup-pending record가 모두 0입니다.
- Provider/resign failure와 campaign-timeout rate가 이전 stable window 대비 상대 20%와
  절대 1 percentage point 범위 안에 있습니다.
- Campaign-wait와 takeover-latency p95가 baseline의 1.2배 이하입니다.
- 모든 cleanup이 2 TTL 안에 bounded retry 또는 TTL fallback으로 끝납니다.
- PostgreSQL pool wait/statement p99가 `Lease-RenewInterval` margin 안에 있고,
  starvation에서 server-time expiry 전에 local leadership이 해제되며, controlled HA
  fencing/takeover exercise가 성공합니다.

Gate 위반, raw identifier/error 노출, goroutine/container leak, 2 TTL을 넘긴 cleanup
pending, 새 owner를 막는 lease가 하나라도 있으면 promotion을 hold합니다. Safety/redaction
위반이 있거나 두 번의 연속 5분 window 동안 회복하지 못하면 rollback합니다.

### Rollback 완료 조건

Binary rollback 전에 service shutdown context로 outstanding campaign을 취소하고 bounded
owner-aware resign을 시도합니다. Campaign goroutine과 renew traffic이 0이고, 모든 cleanup이
끝났거나 남은 TTL이 기록됐으며, resign 또는 TTL expiry 뒤 takeover probe가 성공해야
rollback 완료로 선언합니다. 기존 provider storage format은 바뀌지 않았으므로 data
migration rollback이 필요하지 않습니다. `leader/sql` binary rollback에서는
`public.bluetape_leader_leases`와 grant를 유지합니다. 사용 중인 binary가 없어진 뒤 별도
review된 migration으로만 table을 drop하거나 rewrite합니다.
