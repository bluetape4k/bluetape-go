# 0.3.0 Cache And Coordination Research

## Milestone

0.3.0 - near cache, distributed lock, rate limiting.

## bluetape4k 근거

- `bluetape4k-projects/cache/cache-core`: common cache abstraction.
- `cache/cache-lettuce`, `cache/cache-redisson`, `cache/hibernate-cache-lettuce`: Redis-backed cache 및 near-cache pattern.
- `infra/bucket4j`: token bucket 및 rate limiting 개념.
- `infra/redis`, `infra/lettuce`, `infra/redisson`: distributed lock 및 Redis coordination helper.

## Go 방향

- 작은 cache interface와 loader/stampede-protection pattern을 정의한다.
- dependency API를 넘는 일관된 bluetape-go behavior를 추가할 때만 local cache adapter를 구현한다.
- Pub/Sub invalidation을 가진 Redis-backed near cache를 구현한다.
- RESP3 `CLIENT TRACKING`은 Testcontainers spike가 go-redis push invalidation과 reconnect behavior를 증명한 뒤에만
  future NearCache strategy로 둔다.
- normal CI는 correctness와 race safety에 집중해야 하므로 cache 및 Redis NearCache benchmark evidence는 #107의 opt-in으로 둔다.
- Redis distributed lock은 owner token과 TTL로 구현한다.
- concrete Redis lock API와 single-instance boundary는
  [Issue #24 Redis distributed lock](2026-06-04-issue-24-redis-distributed-lock.md)에 기록한다.
- local 및 Redis token-bucket rate limiting을 구현한다.
- strategic leader election은 deterministic FIFO, seed-stable random, scored strategy를 가진 candidate-registry coordination
  model로 구현한다.
- concrete strategic elector scope는
  [Issue #86 Strategic Leader Elector](2026-06-05-issue-86-strategic-leader-elector.md)에 기록한다.

## Dependency Candidates

- `golang.org/x/sync/singleflight`: stampede protection.
- `github.com/redis/go-redis/v9`: Redis lock, near cache, limiter backend.

## 결정

이 영역에서 bluetape-go의 가치는 또 하나의 generic cache library가 아니라 local 및 Redis-backed variant 전반의
coordination과 consistent behavior다.

Issue #110은 RESP3 client-side caching을 strategy boundary로 유지하지만, low-level `go-redis/v9` `CLIENT TRACKING`
behavior가 증명되기 전에는 production implementation으로 승격하지 않는다.

Issue #107은 `cache.Memory`와 Redis Pub/Sub NearCache에 대해 repeatable benchmark evidence를 추가하되 benchmark execution을
`make ci`의 일부로 만들지 않는다.
