## Risk table

| Risk | Trigger | Signal | Prevention | Recovery | Owner |
|---|---|---|---|---|---|
| Buffered-output checkpoint loss | A later filter or processor skip reaches a chunk boundary while earlier kept output is still buffered | Checkpoint advances beyond durable business rows; restart omits buffered items | Chunk by consumed input and commit pending output with the latest checkpoint in one transaction; do not add an EOF-only revision | Stop the run, restore from the last jointly verified business/checkpoint position, repair chunking, and replay the affected chunk | Core |
| Filter/skip transaction amplification | An all-filter or all-skip stream is checkpointed once per input | Transaction and revision count approaches input count instead of `ceil(inputs / ChunkSize)` | Use consumed-input chunking and suppress the business callback for empty output | Quiesce the job, repair boundary accounting, and rerun exact transaction-count tests before rollout | Core |
| Same-key overlap | Two actors process the same namespace and checkpoint key concurrently | One CAS winner, conflict losers, duplicated external work, or repeated stale retries | Require external same-key serialization; keep revision CAS as the final fence and never auto-retry conflicts | Quiesce every same-key actor, reconcile business rows and checkpoint, then restart one actor from a fresh load | Caller/Ops |
| Missing-row stale resurrection | A stale actor loaded no row, another actor creates or advances it, and the stale actor later attempts create | Unexpected create success or a missing-row attempt overwrites newer progress | Split create and update CAS; allow create only for expected revision zero and make existing-row conflict fail closed | Roll back the stale transaction, stop the stale run, quiesce peers, and restart from a fresh load | Provider |
| Revision exhaustion | Stored revision reaches PostgreSQL `bigint` maximum | Overflow, negative revision, or DB work begins at maximum revision | Check the maximum before beginning DB access and return the typed revision-exhausted error | Stop processing; archive or migrate the namespace under an explicit operator plan before resuming | Provider/Ops |
| Codec drift | Deployed encode/decode logic or checkpoint type changes incompatibly | Decode error, non-canonical round trip, or different bytes for the same checkpoint | Require both typed codec functions, stable versioned encoding, deterministic round-trip tests, and sanitized causal errors | Halt the affected key, deploy a compatible decoder or controlled migration, then load and validate before restart | Caller/Provider |
| Oversized payload | Encoded checkpoint exceeds the configured or 16 MiB hard limit, or a hostile row advertises a large value | Size rejection, memory spike, or payload fetched before bounds are checked | Validate configuration, reject oversized encoded bytes, and project payload only when SQL-side length is within the configured limit | Reject the checkpoint without commit; reduce or migrate the state representation and retry from the prior revision | Provider |
| Callback captured DB or external side effect | `WriteTxFunc` uses a captured pool, client, queue, file, or another session instead of the supplied transaction-bound session | Side effect survives a transaction rollback or has no matching checkpoint revision | Document and test the supplied `sqlkit.Session` as the only DB write path; forbid captured DB and external effects in the callback | Quiesce the key and manually reconcile the external/business effect with checkpoint state; do not automatically replay | Caller |
| Raw `COMMIT` or `ROLLBACK` | Callback issues transaction control directly or through a procedure | Reserved savepoint disappears, `sql.ErrTxDone`, SQLSTATE `3B001` or `25P01`, or ownership probe cannot prove the original transaction | Create a private reserved savepoint, run the ownership probe on return and panic, and dispatch no checkpoint DML or provider `Commit` unless ownership is proven | Positive lifecycle evidence preserves callback contract violation plus atomicity-unknown and commit-unknown; ambiguous cancellation, transport, bad-connection, or unclassified probe failure preserves both unknown sentinels without guessing contract violation; quiesce and reconcile manually | Provider/Caller |
| `COMMIT` to `BEGIN` to failed SQL | Callback commits the owned transaction, starts another, then leaves it failed | Probe sees `25P02`, but `ROLLBACK TO` the reserved guard fails because it belongs to the prior transaction | Treat `25P02` as insufficient; require successful `ROLLBACK TO SAVEPOINT` against the reserved guard to prove ownership | Mark atomicity unknown, roll back what can be rolled back, quiesce the key, and manually reconcile both transaction histories | Provider |
| Panic after raw `COMMIT` | Callback commits and then panics before returning | Original panic plus missing guard; business rows may exist without checkpoint CAS | Run the ownership probe in the deferred panic path and sanitize provider text while preserving the original panic value | Re-panic as sanitized `AtomicityPanic` whose unwrap chain preserves atomicity-unknown and commit-unknown; expose the original panic only through the trusted `PanicValue` diagnostic accessor; supervisor must quiesce and require manual reconciliation | Provider/Caller |
| Ownership-probe timeout | Lock contention, pool pressure, network delay, or cancellation stalls the reserved-savepoint probe | Probe exceeds one second plus bounded scheduler tolerance; no reliable ownership verdict | Use a bounded probe context and guarantee that proof failure dispatches neither checkpoint DML nor provider-owned `Commit` | Cancel and release resources, classify the outcome as atomicity unknown, drain pressure, and reconcile before retry | Provider/Ops |
| Provider-`Commit` response loss | `tx.Commit()` is dispatched but the response is lost or returns an ambiguous transport error | Zero revision with `ErrCommitUnknown`; DB state may show either old or next revision | Call provider `Commit` exactly once, never retry automatically, and distinguish provider-commit unknown from ownership unknown | With same-key actors quiesced, fresh-load and reconcile only when `ErrAtomicityUnknown` is absent; otherwise perform manual business/checkpoint reconciliation | Caller/Ops |
| Cancellation races | Context is canceled before begin, during callback/probe, at checkpoint DML, or after commit dispatch | Late rows, leaked connection, `sql.ErrTxDone`, discarded confirmed commit, or ambiguous zero revision | Preflight before DB access; prove ownership and full rollback for known cancellation; preserve confirmed post-commit success and never automatically retry caller cancellation | A caller/operator may deliberately restart a known, fully rolled-back cancellation only after a fresh load verifies the prior checkpoint; for ownership or commit unknown, quiesce and reconcile before resuming | Provider/Core/Caller/Ops |
| Pool starvation | Long callbacks, probe waits, canceled work, or concurrent jobs consume all pool connections | `DBStats.WaitCount` and wait duration rise; probe/callback timeouts; connections do not return after cancellation | Bound callback/probe contexts, keep one owned transaction per commit, release on every path, and test small-pool drain behavior sequentially | Stop intake, cancel and drain stuck work, restore pool headroom, then rerun the bounded pool test | Caller/Ops |
| Unlogged, temporary, or hostile relation | Migration finds an existing object with the expected name but unsafe persistence, kind, columns, constraints, or ownership | `pg_class.relpersistence` is not `p`, relation kind or catalog shape differs, or constraint validation fails | Migration owner performs catalog preflight for a permanent ordinary table with exact owner, columns, PK, and validated checks; `IF NOT EXISTS` is not proof | Fail readiness before writes; remove or rename the hostile object as migration owner and recreate the approved schema | Security/Ops |
| RLS, trigger, or rewrite drift | Policy, user trigger, forced RLS, or rewrite rule is added after deployment | Hidden rows, redirected writes, nonzero policy/user-trigger/rewrite catalog entries | Verify RLS and forced RLS off, zero policies, zero user triggers, and zero user `pg_rewrite` rules during readiness | Block the provider, restore the verified catalog state, audit affected writes, and rerun hostile-schema tests | Security/Ops |
| Schema, table, or column ACL drift | Grants, membership, owner, or PUBLIC privileges change | Runtime can perform DDL or cannot perform required DML; unexpected inherited or column privilege appears | Validate direct, inherited, and PUBLIC schema/table/column ACLs; separate non-login owner, migration role, and least-privilege runtime role | Revoke excessive grants or restore required grants, rotate compromised roles, and rerun readiness before traffic | Security/Ops |
| PUBLIC object creation | PUBLIC retains schema `CREATE` while the checkpoint object is bootstrapped | Untrusted actor wins the object name or replaces expected shape before migration | Revoke PUBLIC schema `CREATE` under bounded lock and statement timeouts before creating the table | Fail deployment, remove the hostile object as the migration owner, reapply grants, and repeat catalog verification | Security/Ops |
| WAL, dead-tuple, replication, or retention pressure | Every chunk updates one checkpoint row under sustained workload, replicas lag, or retention targets active rows | WAL rate, dead tuples, table/index size, autovacuum lag, replication lag, or retention backlog crosses the canary gate | Use isolated canary traffic; monitor `DBStats`, relation size, dead tuples, WAL, autovacuum, and replication with workload-specific thresholds; forbid active-row deletion or key reuse until all runs are quiesced and joined and every unknown outcome is reconciled | Pause canary/intake, tune retention or vacuum safely without deleting active rows, restore replication health, and roll back the provider if pressure persists | Ops |
| Legacy cutover | A job moves from the legacy checkpoint path to the SQL atomic provider while old actors or intake remain active | Old and new actors overlap, positions disagree, or both providers advance independently | Quiesce intake and cancel/join old runs; export the exact authoritative legacy safe position; seed the exact namespace/key with the agreed codec and read it back for comparison; block mixed old/new binaries; isolate both checkpoint and business-data cohorts before starting exactly one canary actor | Stop the new actor, preserve both states, reconcile business progress manually, and resume only one provider | Caller/Ops |
| Rollback | Canary or production acceptance fails after SQL checkpoint adoption | Error, latency, storage, privilege, or recovery gate breaches its rollback threshold | Define rollback thresholds and observation window before cutover; preserve old state, roles, and grants throughout that window | Quiesce and join SQL actors, reconcile SQL business/checkpoint state, export the reconciled SQL position into the legacy store and read it back for comparison, or choose an explicitly operator-approved safe replay position; then restore the legacy path and retain SQL evidence | Caller/Ops |
| Supervisor automatic panic replay | A generic top-level recover loop treats `AtomicityPanic` like an ordinary transient panic | Same chunk is automatically replayed after transaction ownership became unknown | At the top-level recover boundary, test `errors.Is(recoveredError, ErrAtomicityUnknown)` first and prohibit automatic replay | Quiesce same-key intake and runs, manually reconcile business/checkpoint state, then restart under operator approval | Caller/Ops |
| Testcontainers leakage | A pool, connection, goroutine, or container outlives a PostgreSQL test fixture | Test hang, leftover containers, exhausted ports, or subsequent suite interference | Run Docker-backed suites sequentially, use bounded contexts and LIFO cleanup, and assert pool/connection release on every failure path | Terminate the leaked fixture, verify Docker and pool cleanup, and rerun the command from scratch | Tests |
| Bilingual or diagram drift | Public behavior changes without paired locale or rendered sequence updates | English and Korean READMEs disagree, missing embed, stale SVG/PNG pair, or diagram omits a recovery branch | Update English/Korean package and root inventory together; generate paired SVG/PNG and audit the full-size rendering against the settled contract | Block PR progression, repair both locales and both assets, rerun doc/reference checks, and visually review again | Docs |

## Stop conditions

- Any P0/P1 finding, missing exit code, artifact hash drift, non-artifact pre-risk change, or baseline
  failure blocks source work.
- Any unproven transaction ownership path must dispatch neither checkpoint DML nor provider-owned
  `Commit`; it requires same-key quiescence and manual reconciliation.
- A first failure that passes only on retry remains a stability investigation, not passing evidence.
- Testcontainers-backed commands remain sequential, and no benchmark or capacity claim is added
  under Issue #532.
