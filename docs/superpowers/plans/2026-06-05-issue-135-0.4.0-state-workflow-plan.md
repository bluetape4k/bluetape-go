## Execution Principles

- Use feature worktrees for issue work.
- Keep PRs small and ordered by dependency.
- Keep implementation first-party unless a dependency is explicitly justified.
- Prefer ordinary Go APIs over Kotlin-style DSL ports.
- Add docs, examples, stress/cancellation tests, and race validation as part of
  the package contract, not as afterthoughts.

## #26 Implementation Plan Shape

- Create `state` package skeleton: `doc.go`, `errors.go`, API files, tests, and
  examples.
- Define transition and guard contracts.
- Validate duplicate transitions and missing initial state.
- Implement concurrency-safe state changes.
- Add unit tests for valid transition, invalid transition, guard rejection,
  final state, allowed events, and context cancellation.
- Add stress/race tests for concurrent transition attempts.
- Add package README and later link it through #132.

## #28 Implementation Plan Shape

- Create `workreport` package skeleton.
- Define `Status`, `FailurePolicy`, `Report`, helper constructors, and helper
  predicates.
- Define aggregation rules for sequential and parallel consumers.
- Preserve child report order where deterministic.
- Add tests for every status and aggregation path.
- Document zero-value behavior.
- Add package README and examples.

## #27 Implementation Plan Shape

- Create `workflow` package skeleton.
- Define `Work` and `Runner` contracts.
- Implement sequential runner first.
- Implement conditional runner second.
- Implement parallel runner last, because cancellation and aggregation behavior
  are the hardest part.
- Keep caller context as the cancellation carrier.
- Do not add a mutable shared context map unless the implementation evidence
  shows examples become awkward without it.
- Add stress/race tests for parallel runner cancellation and aggregation.

- #135: docs-only review for consistency with issue bodies and current repo
  evidence.

- Any P0/P1 finding blocks the next issue.
- PR body final section must be `## DoD Status`.

## Stop Conditions

- Stop #135 when the research/spec/plan are committed, PR is open, and issue #4
  references #135/#136/#137.
- Stop implementation issues only after targeted tests, race tests, examples,
  README/docs checks, review gate, PR creation, and CI evidence.

## Known Risks

| Risk | Mitigation |
|---|---|
| API grows into a Kotlin DSL port | Keep package split and public API explicit; reject reflection-heavy builders for 0.4.0. |
| Workflow package owns too many concepts | Keep report model in `workreport`; keep `state` independent. |
| Cancellation is underspecified | #136 requires explicit stress/cancellation tests. |
| Examples drift from docs | #137 requires compile-checked examples; #132 links README to examples. |
| Parallel runner leaks goroutines | Require cancellation tests and race validation before #27 closes. |
