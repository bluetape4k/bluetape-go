## 맥락

0.4.0 starts a new public surface for finite state machines and lightweight
workflow runners. The Kotlin `utils/states` and `utils/workflow` modules prove
the domain concepts, but bluetape-go should not reproduce Kotlin DSL,
coroutine, reactive, or Virtual Thread layers.

The milestone must establish small Go packages that are easy to test, document,
and compose with `context.Context`.

## 목표s

- Define a small `state` package for finite state machines.
- Define a `workreport` package for workflow result and policy values.
- Define a `workflow` package for sequential, parallel, and conditional runners.
- Keep all three packages first-party, dependency-light, and framework-free.
- Preserve context cancellation semantics in every runner API.
- Add stress/cancellation coverage for concurrent or timing-sensitive behavior.
- Add package READMEs, compile-checked examples, and source-grounded diagrams
  after the public API stabilizes.

## Non-Goals

- Do not add a durable workflow engine.
- Do not add a reflection-heavy Kotlin-style DSL.
- Do not implement repeat/retry runners in 0.4.0; those belong to later
  workflow or batch milestones.
- Do not add coroutine, reactive, observer, or event/effect runtimes.
- Do not add a default mutable shared context map unless #27 proves ordinary
  Go closures and explicit input/output are insufficient.
- Do not make benchmark numbers a 0.4.0 release gate before the API exists.

This split avoids import cycles: `workflow` imports `workreport`; `state` is

## `state` API Direction

The package should use comparable state and event values and keep transition
definitions explicit.

Expected concepts:

```go
type Guard[S comparable, E comparable] func(context.Context, S, E) error

type Transition[S comparable, E comparable] struct {
    From  S
    Event E
    To    S
    Guard Guard[S, E]
}

type Result[S comparable, E comparable] struct {
    Previous S
    Event    E
    Current  S
}
```

The implementation shape can be refined in #26, but the behavior contract must
include:

- `NewMachine` validates initial state and transition definitions.
- `State` returns the current state.
- `Transition(ctx, event)` applies exactly one valid transition or returns an
  error without changing state.
- `CanTransition(ctx, event)` evaluates the current transition and guard
  without changing state.
- `AllowedEvents` returns only events valid from the current state.
- final states reject further transitions.
- guards run with the caller context and can veto a transition with an error.
- public methods are safe for concurrent callers.
- no callback runs while holding an internal lock unless the implementation
  proves no deadlock risk.

Error requirements:

- callers can distinguish invalid transition, guard rejection, final state, and
  concurrent state conflict where applicable.
- `errors.Is` or typed error inspection should be possible for common cases.

## `workreport` API Direction

The package should make workflow outcomes explicit without requiring a workflow
runner.

Expected concepts:

```go
type Status string

const (
    StatusCompleted Status = "completed"
    StatusFailed    Status = "failed"
    StatusPartial   Status = "partial"
    StatusAborted   Status = "aborted"
    StatusCancelled Status = "cancelled"
)

type FailurePolicy int

const (
    StopOnFailure FailurePolicy = iota
    ContinueOnFailure
)

type Report struct {
    Name       string
    Status     Status
    StartedAt  time.Time
    EndedAt    time.Time
    Err        error
    Reason     string
    Children   []Report
}
```

The implementation shape can be refined in #28, but the behavior contract must
include:

- reports have stable statuses and helper predicates.
- failed, aborted, and cancelled are terminal for a single work result.
- partial reports preserve child failures.
- aggregation preserves child order when order is deterministic.
- report helpers do not hide errors behind strings.
- zero-value report behavior is documented.

## `workflow` API Direction

The package should compose ordinary Go work functions.

Expected concepts:

```go
type Work func(context.Context) workreport.Report

type Runner interface {
    Run(context.Context) workreport.Report
}
```

Required runners:

- sequential runner
- parallel runner
- conditional runner

Sequential behavior:

- runs works in order.
- `StopOnFailure` returns the first failure.
- `ContinueOnFailure` accumulates failures and returns partial when any child
  failed.
- aborted and cancelled stop immediately regardless of failure policy.

Parallel behavior:

- supports all-branches semantics.
- optionally supports any-success semantics if the API can stay small.
- propagates caller cancellation.
- does not leak goroutines after cancellation.
- preserves enough child report detail for debugging.

Conditional behavior:

- evaluates one predicate.
- runs exactly one selected branch.
- returns completed when no false branch exists and the predicate is false.
- propagates predicate errors as failed reports if the final API allows
  error-returning predicates.

## Documentation Requirements

- Every new package has `doc.go` and package `README.md`.
- Root `README.md` and `README.ko.md` link to new package READMEs once packages
  exist.
- Each public package has at least one compile-checked `Example*`.
- Diagrams are added only after APIs stabilize and must be source-grounded.
- Public docs and GitHub artifacts are in English.

## Test Requirements

- Unit tests cover all status and transition branches.
- `GoroutineStressTester` covers concurrent state transitions and parallel
  runner execution where meaningful.
- `AsyncJobTester` covers cancellation/deadline propagation.
- `go test -race` is part of the targeted verification for `state`,
  `workreport`, and `workflow` once code exists.
