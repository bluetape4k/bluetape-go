# Issue 135 0.4.0 State And Workflow Inventory

Issue: #135
Milestone: 0.4.0
Epic: #4

## Purpose

Refresh the 0.4.0 planning evidence before implementing the Go state and
workflow packages. The Kotlin modules are reference material only; the Go
surface should stay small, first-party, framework-free, and idiomatic.

## Current bluetape-go Baseline

The current repository has no `state`, `workflow`, or `workreport` packages.
CodeGraph indexed the current tree with 151 Go files and shows the existing
public packages follow a repeatable shape:

- package-level `doc.go`
- small public API files
- package README files for user-facing behavior
- compile-checked `Example*` tests
- targeted stress/cancellation tests where concurrency is part of the contract

The 0.3.0 WIP and lessons add these guardrails for 0.4.0:

- Keep public packages Go-first and avoid mechanical Kotlin extension ports.
- Prefer small packages over catch-all utility bags.
- Use `GoroutineStressTester` and `AsyncJobTester` for concurrency and
  cancellation contracts.
- Keep package usage and behavior in package READMEs; keep root README as an
  index.
- Use first-party implementation for new infrastructure packages unless a
  dependency is explicitly justified.

Useful concepts to carry forward:

- status taxonomy: completed, failed, partial, aborted, cancelled
- explicit stop/continue failure strategy
- sequential runner with failure accumulation under continue policy
- parallel runner with all/any policy semantics
- conditional runner that picks exactly one branch
- report-first execution, where control flow is visible to callers
- cancelled and aborted outcomes are terminal regardless of ordinary failure
  policy

Concepts to defer or exclude from 0.4.0:

- Kotlin DSL syntax as a direct Go target
- suspend/coroutine variants
- JVM Virtual Thread execution model
- repeat/retry workflow runners
- mutable `WorkContext` as a default requirement
- benchmark comparison between execution models

Go implication: a workflow runner should be a small `context.Context`-driven
composition layer. Work functions should return a report, not panic or hide
control flow. Parallel semantics may use `golang.org/x/sync/errgroup` where it
matches cancellation and aggregation needs, but the public API should not expose
`errgroup`.

## Dependency Position

Do not add a workflow engine dependency in 0.4.0. The targeted API is small and
the value is predictable Go behavior. Reuse the existing `golang.org/x/sync`
dependency only if it makes #27 simpler without leaking into the public API.

## Open Design Questions For Spec

- Whether state machine methods should return typed sentinel errors or one
  structured transition error type.
- Whether `workreport` should be a separate package or live under `workflow`.
- Whether workflow work functions need a mutable state bag, or whether examples
  can use ordinary closures and caller-owned data.
- How much failure aggregation belongs in `workreport` versus runner-specific
  helpers.

## Research Conclusion

The smallest safe 0.4.0 split is:

- `state`: finite state machine with guards, final states, transition results,
  and concurrency-safe state changes.
- `workreport`: shared report/status/failure policy model.
- `workflow`: sequential, parallel, and conditional runners that consume
  `workreport` and `context.Context`.

That split keeps #26 independent, lets #28 define the reporting contract before
#27 consumes it, and leaves README/example/diagram work to run after the public
API stabilizes.
