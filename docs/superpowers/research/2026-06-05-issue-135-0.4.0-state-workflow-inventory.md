151 Go files로 index했고, 기존 public package가 반복 가능한 shape를 따른다는 점을 보여준다.

- package-level `doc.go`
- 작은 public API file
- user-facing behavior를 위한 package README

- concurrency가 contract 일부일 때 targeted stress/cancellation tests

0.3.0 WIP와 lesson은 0.4.0에 다음 guardrail을 추가한다.

- public package는 Go-first로 유지하고 Kotlin extension port를 기계적으로 복사하지 않는다.
- catch-all utility bag보다 작은 package를 선호한다.
- concurrency와 cancellation contract에는 `GoroutineStressTester`와 `AsyncJobTester`를 사용한다.
- package usage와 behavior는 package README에 두고 root README는 index로 유지한다.
- dependency가 명시적으로 정당화되지 않는 한 새 infrastructure package는 first-party implementation을 사용한다.

가져올 concept:

- completed, failed, partial, aborted, cancelled status taxonomy
- explicit stop/continue failure strategy
- continue policy 아래 failure accumulation을 하는 sequential runner
- all/any policy semantics가 있는 parallel runner
- 정확히 하나의 branch를 선택하는 conditional runner
- control flow가 caller에게 보이는 report-first execution
- cancelled와 aborted outcome은 ordinary failure policy와 무관하게 terminal

미루거나 제외할 concept:

- Kotlin DSL syntax를 직접 Go target으로 삼기
- suspend/coroutine variants
- JVM Virtual Thread execution model
- repeat/retry workflow runners
- mutable `WorkContext`를 default requirement로 삼기
- execution model 간 benchmark comparison

Go implication: workflow runner는 작은 `context.Context`-driven composition layer여야 한다.
work function은 panic하거나 control flow를 숨기지 말고 report를 반환해야 한다. parallel semantics는
cancellation과 aggregation에 맞을 때 `golang.org/x/sync/errgroup`를 사용할 수 있지만, public API가
`errgroup`를 노출하면 안 된다.

## Dependency Position

0.4.0에서는 workflow engine dependency를 추가하지 않는다. 목표 API는 작고, 가치는 predictable
Go behavior다. #27을 단순하게 만들면서 public API로 leak하지 않을 때만 기존
`golang.org/x/sync` dependency를 재사용한다.

## Spec을 위한 Open Design Questions

- state machine method가 typed sentinel error를 반환할지, 하나의 structured transition error type을 사용할지.
- `workreport`를 별도 package로 둘지 `workflow` 아래에 둘지.
- workflow work function이 mutable state bag을 필요로 하는지, 아니면 example이 ordinary closure와 caller-owned data로 충분한지.
- failure aggregation이 `workreport`에 얼마나 들어가고 runner-specific helper에 얼마나 남아야 하는지.

## Research Conclusion

가장 작은 safe 0.4.0 split은 다음과 같다.

- `state`: guard, final state, transition result, concurrency-safe state change를 가진 finite state machine.
- `workreport`: shared report/status/failure policy model.
- `workflow`: `workreport`와 `context.Context`를 소비하는 sequential, parallel, conditional runner.

이 split은 #26을 독립적으로 유지하고, #28이 #27보다 먼저 reporting contract를 정의하게 하며,
public API가 안정된 뒤 README/example/diagram work가 이어지게 한다.
