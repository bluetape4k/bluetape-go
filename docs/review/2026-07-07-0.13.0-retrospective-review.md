## 발견 사항

### P1-1: `cache.Memory.GetOrLoad` lets the first caller's cancellation fail live same-key waiters

상태: confirmed P1, fix under #425.

Evidence:

- `cache/memory.go:151` derives a `singleflight` key for the public cache key,
  and `cache/memory.go:152-178` runs one shared loader closure.
- That shared closure captures the first caller's `ctx`: it checks that context
  at `cache/memory.go:160-162`, calls `loader(ctx, key)` at
  `cache/memory.go:164`, checks it again at `cache/memory.go:169-172`, and
  writes through `Set(ctx, ...)` at `cache/memory.go:173`.
- Other callers only select on their own `ctx` while receiving the shared call
  result at `cache/memory.go:180-192`. If the owner context is canceled while a
  live waiter is attached, the live waiter receives `context.Canceled` from the
  owner call even though its own context is still valid.
- Existing tests prove same-key success collapse
  (`cache/memory_test.go:214-245`) and unique-key loader cancellation
  (`cache/memory_test.go:311-341`), but do not prove same-key cancellation
  isolation.
- Temporary non-committed reproduction:
  `go test -count=1 ./cache -run TestMemoryGetOrLoadFirstCallerCancellationDoesNotFailWaiterRepro`
  failed with `waiter with live context got error: context canceled` after the
  waiter was held on the in-flight first load before the owner loader was
  released.

Impact:

- The cache README advertises context-aware loaders and same-key stampede
  protection (`README.md:83`, `cache/README.md:5-8`, `cache/README.md:41-42`).
  A canceled first caller can therefore deny a same-key request that still has a
  valid context.
- This matches the `bluetape-go-patterns` P1 rule for cache/stampede adapters
  that leak cancellation effects across caller boundaries.

Required fix:

- Preserve per-caller cancellation for waiters. A live waiter should either
  retry after a shared context-cancellation result or the shared load should run
  under an owner context whose cancellation cannot be borrowed from an arbitrary
  first waiter. Add a regression test that proves same-key live waiters do not
  fail because the owner caller canceled.

### P1-2: `ratelimit/redis` trims caller-owned logical keys before storage

상태: confirmed P1, fix under #425.

Evidence:

- `ratelimit/redis/README.md:48-52` documents the Redis key shape as
  `bluetape:ratelimit:<namespace>:bucket:<key>`, with `<key>` supplied to
  `Allow`.
- `ratelimit/redis/limiter.go:91` replaces the caller key with
  `l.normalizeKey(key)`.
- `ratelimit/redis/limiter.go:123-131` uses `strings.TrimSpace(key)` and
  returns the trimmed value for storage, so `"tenant:blue"` and
  `" tenant:blue "` collapse into the same Redis bucket.
- `ratelimit/redis/limiter_test.go:157-183` covers blank and too-long keys but
  does not assert verbatim key preservation or whitespace-distinct collision
  behavior.
- The earlier Redis lock lesson already fixed this exact class:
  `docs/lessons/2026-06-04-issue-24-redis-distributed-lock.md:17-19` says
  validation may inspect normalized text, but Redis packages should store the
  exact caller-provided key unless canonicalization is explicitly documented.
- The lock package follows that lesson: `lock/redis/options.go:26-36` validates
  with `strings.TrimSpace(o.Key)` but stores `key: o.Key`.

Impact:

- Distinct caller-owned tenants, subjects, or route keys can be rate-limited as
  the same Redis bucket without an explicit canonicalization contract.
- This matches the `bluetape-go-patterns` P1 rule for generic/Redis APIs that
  trim or normalize caller-owned Redis/cache keys without explicit
  canonicalization.

Required fix:

- Reject blank keys by checking `strings.TrimSpace(key) == ""`, but preserve the
  original `key` for byte-length validation and Redis storage unless the public
  README and tests intentionally define a canonicalization contract. Add tests
  proving whitespace-distinct keys do not share a bucket or storage key.
